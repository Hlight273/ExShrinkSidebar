# Git 提交日志

生成可直接用于 Git 提交的中文信息，方便日后按功能查阅。每个主题采用“带前缀的标题 + 空行 + 修改细节”的格式，以实际改动为依据，适用于不同项目，不依赖特定作者或仓库历史。

## 确定改动范围

- 用户指定文件、提交、提交区间或提供 diff 时，按指定范围生成。
- 未指定范围时，先查看 `git status --short`、`git diff --cached --stat` 和 `git diff --cached`。暂存区有改动时，仅总结暂存区；同时存在未暂存改动时，在日志代码块外简短注明范围。
- 暂存区为空时，查看 `git diff --stat` 和 `git diff`，根据工作区生成待提交草稿并注明范围。未跟踪文件不会出现在 diff 中，需要读取其相关内容才能纳入总结。
- 读取差异被截断时，按文件继续查看，不能只凭文件名或统计量推断功能。仅在理解改动确有需要时补读相关代码或文档，并遵守当前仓库的适用规则。
- 没有实际改动且用户未提供改动说明时，说明缺少生成依据，不编造日志。
- 用户要求参考当前仓库的历史措辞时，可读取 `git log -12 --no-merges --format=%B`，但不照搬与当前改动无关的内容。默认直接按本技能格式生成，不要求存在历史提交。

## 选择前缀

| 前缀 | 使用场景 |
| --- | --- |
| `feat:` | 新功能、新能力或新增用户可用的业务行为 |
| `refactor:` | 重构、结构整理或优化，主要目的不是修复缺陷或增加新功能 |
| `fix:` | 修复 bug、错误行为或回归问题 |
| `docs:` | 仅修改文档、说明或注释 |
| `chore:` | 工具维护、工程杂项等不适合以上类别的变更 |

- 按每个主题的主要目的分别选择前缀，不按修改文件数量决定。功能附带文档更新时，仍使用对应的功能前缀。
- `chore:` 不是未读懂差异时的兜底；先弄清改动用途。
- 默认严格使用 `类型: 主题`，英文冒号后留一个空格。仅在用户明确要求 scope 时使用 `类型(scope): 主题`。
- 每个主题都有自己的标题前缀；同一条提交信息可以包含多个主题，也可以同时包含 `feat:`、`fix:`、`refactor:` 等不同前缀。

## 多模块改动

先按业务目的归组，再决定日志结构；不能仅因改动分布在多个目录、客户端和服务端，就判断为多个独立功能。

- **同一功能涉及多个模块**：使用一个主题标题，将协作模块的修改写入细节。例如登录界面、认证接口和会话存储共同完成登录功能，应归为同一个 `feat:` 主题。
- **主功能附带修复或文档更新**：标题与前缀仍由主功能决定，在细节中保留重要的附带改动，不为每个模块重复添加提交标题。
- **多个模块功能或独立修复**：在同一条日志中依次写出各自的 `类型: 模块或功能主题`，每个主题下只列出属于该主题的细节。主题之间空一行，不增加共用总标题，不把不同功能合并成一个主题。
- **不同主题属于不同类型**：分别选择前缀，例如新增导出功能用 `feat:`，修复搜索问题用 `fix:`，重构缓存模块用 `refactor:`；不为整条日志选一个统一前缀。
- **主题排序与边界**：主要功能在前，其余主题按业务关联排列。同一文件中的不同功能改动可分别归入对应主题；公共改动放在最相关的主题下说明，避免重复罗列。
- **日志分主题不等于拆分 Git 提交**：默认仍生成一条包含多个主题的完整提交信息。只有用户要求拆分提交时，才分别提供多条日志及对应改动范围；不自行暂存或拆分。

多主题提交信息示例（仅展示结构）：

```text
feat: 增加报表导出功能

- 支持将筛选结果导出为 CSV 文件
- 在导出文件中保留当前列顺序

fix: 修复搜索分页结果重复

- 调整分页边界，避免相邻页面出现重复记录
- 修改搜索条件后重置页码
```

## 组织内容

每个主题先写带前缀的模块或功能标题，使用“新增”“接入”“修复”“统一”“重构”等具体动词，让读者只看标题也能知道该主题的修改目的。避免“更新代码”“修复问题”“一些优化”等空泛描述。

标题后空一行，使用 `-` 列出值得后续查阅的修改细节：

- 优先说明业务行为、规则变化、修复结果，其次说明必要的接口、数据、生命周期或文档变更。
- 同一功能的零散修改合并描述，不逐文件罗列，不重复标题；条数随实际改动复杂度调整，不为凑数补充内容。
- 保留有查阅价值的模块名、接口名、关键参数和变化前后的行为。路径仅在定位具体修改确有必要时出现。
- 修复类优先说明触发条件与修复后的结果；重构类说明结构或职责如何调整及其收益。
- 简单改动可以只写一条细节；已有具体信息不足以补充细节时，允许只保留准确标题，不能编造。
- 不声称未实际完成的测试、验证、性能收益、同步、发布或归档。不把计划中的修改写成已完成。
- 中文描述，保留代码标识符原文。标题不加句末标点，细节使用简洁、完整的短句。

## 输出

默认输出一个 `text` 代码块，包含所有主题及各自细节，可整体复制为一次提交的信息。只有用户明确要求拆分提交时，才为每条提交使用单独的代码块。必要的范围说明放在代码块外；用户只要日志时，不附加分析或备选版本。

格式示例（仅展示结构，内容必须替换为真实改动）：

```text
feat: 增加任务列表筛选功能

- 支持按任务状态和创建时间筛选
- 在筛选条件变化后刷新列表与结果数量
- 更新筛选参数的接口文档
```

生成日志本身不执行 `git add`、`git commit`、`git push` 或修改 Git 配置。用户明确要求执行提交等操作时，再按其已授权范围和仓库规则处理。
